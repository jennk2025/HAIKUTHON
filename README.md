# HAIKUTHON — Multimodal RAG: 텍스트→이미지 검색

텍스트 설명에 가장 잘 맞는 이미지를 비슷한 이미지들 사이에서 찾는 데이터톤이다.

> 이 문서의 본문에는 **대회 조건, 평가 방식, 규정, 확인할 사항**만 정리했다.
> 본문 내용은 운영진이 공지한 대회 세부 정보를 기준으로 한다. 공지에 없는 내용은 **확인 필요**로 표시했다.
> 구현 방법은 문서 끝의 **[<예시> 구현 참고안](#예시-구현-참고안)**에 따로 모았다. 정해진 계획이 아니고 참고용이다.

## 1. 대회 개요

| 항목 | 내용 |
|---|---|
| 주제 | Multimodal RAG — 텍스트 설명에 가장 적합한 이미지 검색 |
| 핵심 난점 | 비슷한 이미지 사이에서 문장의 세부 내용(색상, 객체, 개수, 행동, 위치, 관계 등)에 맞는 이미지를 골라야 한다 |
| 요구 사항 | 수천~수만 장에서 **정확하고 빠르게** 검색. 제한된 추론 시간 안에서 정확도와 연산 효율을 함께 고려 |
| 데이터 출처 | 운영진이 자체 제작한 **AI 생성 데이터** |

### 데이터셋

| 구분 | 규모 | 공개 여부 |
|---|---|---|
| Train | 텍스트–이미지 **4,000쌍** | Hugging Face에서 다운로드 가능 |
| Test | 텍스트 **8,000개**, 이미지 **16,000장** | **비공개**. 채점 사이트에서 예측 결과만 확인 가능 |

- Test는 질의 8,000개 각각에 대해 이미지 16,000장 중에서 검색한다.
- Test 이미지가 텍스트보다 2배 많다. 정답이 아닌 이미지(distractor)가 섞여 있다는 뜻이다. 구성 방식(비슷한 이미지끼리 짝을 지었는지 등)은 공지되지 않았다.
- Test 이미지가 비공개이므로 **gallery 임베딩을 미리 계산해 ZIP에 넣을 수 없다.** 이미지 인코딩은 평가 환경에서 해야 한다.

### 작업 원칙
- 아이디어만 나열하지 않는다. 가능한 작업은 코드와 측정 결과로 남긴다.
- 데이터·환경·규정에서 확인하지 못한 내용은 사실처럼 가정하지 않는다.
- 임의의 제출 인터페이스를 만들지 않는다. sample_submission을 따른다.

## 2. 평가 방식

### 최종 점수

| 구성 | 비중 | 세부 |
|---|---|---|
| 리더보드 점수 | **70%** | Public **40%** + Private **60%**. Private 점수는 제출 마감 이후 공개 |
| 발표 점수 | **30%** | 심사위원 4명. 발표 전달력, 방법론의 타당성과 독창성, 심사위원 자유 점수 |

- 리더보드에서는 Private 비중이 더 크다. Public 점수에만 맞춘 조정은 피하고, 로컬 검증에서 개선된 구성만 제출한다.
- 발표가 30%이므로 작업 과정과 근거를 [`PUSH_LOG.md`](PUSH_LOG.md)에 계속 기록한다.

### 검색 점수

```
질의별 점수   = 0.5 × (Hit-Ratio@1 + NDCG@5)
최종 검색 점수 = 전체 질의별 점수의 평균
```

- `r` = 정답 이미지의 검색 순위
- **Hit-Ratio@1**: r = 1이면 1, 아니면 0
- **NDCG@5**: r ≤ 5이면 1 / log2(r + 1), 아니면 0

순위별 질의 점수 (공식에서 계산한 값):

| 정답 순위 r | Hit@1 | NDCG@5 | 질의 점수 |
|---|---|---|---|
| 1 | 1 | 1.000 | **1.000** |
| 2 | 0 | 0.631 | 0.315 |
| 3 | 0 | 0.500 | 0.250 |
| 4 | 0 | 0.431 | 0.215 |
| 5 | 0 | 0.387 | 0.193 |
| 6 이상 | 0 | 0 | 0 |

- 1위와 2위의 차이(0.685)가 2위와 탈락의 차이(0.315)보다 훨씬 크다. **정답을 1위에 놓는 정확도가 가장 중요하다.**
- 2~5위도 부분 점수가 있으므로 상위 5개는 모두 의미 있는 순서로 채운다.
- 공식 정의에 `r`이 하나만 나온다. 질의당 정답 이미지는 1장으로 보인다. (확인 필요)

## 3. 실행 환경과 제출 규칙

| 항목 | 내용 |
|---|---|
| GPU | NVIDIA **L4** Tensor Core GPU **10장**, 장당 VRAM **24GB** (안내된 자원) |
| 추론 시간 | 제출 1회당 최대 **15분(900초)**. 모델 로딩 시간 등을 제외한 **추론 시간만** 측정 |
| 제출 횟수 | 팀당 최대 **25회** |
| ZIP 용량 | **5GB 이하** |
| 인터페이스 | sample_submission의 인터페이스를 지키면 모델 구현은 자유 |

### 제출 절차
1. 모델과 실행 코드를 ZIP으로 묶어 평가 시스템에 제출한다.
2. 평가 시스템이 Test 예측 CSV를 만든다.
3. 그 CSV를 내려받아 Kaggle에 제출한다.

## 4. 금지 사항과 문항 독립성

### 공식 금지 사항
1. **외부 API 호출 금지.** 추론은 ZIP에 넣은 로컬 모델과 코드만으로 끝나야 한다.
2. **다른 문항의 예측 결과로 현재 문항의 예측을 보정·수정하는 행위 금지.**

### 2번 규정에 해당하는 것으로 보는 예
`predict(query, gallery, fixed_model)`의 결과는 다른 query의 내용, 처리 순서, 예측 결과에 의존하면 안 된다.

- 다른 문항의 예측으로 현재 문항 점수를 보정
- test query 전체의 점수 통계로 정규화
- 전체 query 사이에서 정답 이미지를 일대일로 배정 (예: 8,000개 query와 16,000장 이미지를 헝가리안 매칭)
- 이전 문항에서 고른 이미지를 현재 문항 후보에서 제거
- 다른 문항의 예측으로 의사 라벨을 만들어 적응

### 규정 위반이 아닌 것으로 보는 예 (공식 확인 권장)
- 독립적인 문항을 배치로 묶어 계산 (결과가 배치 구성과 무관하면 보정이 아니다)
- gallery 이미지만으로 만든 임베딩·검색 인덱스를 평가 중에 한 번 계산해 모든 query에 재사용
- 현재 query 하나의 후보들 안에서 재정렬

## 6. 제출 전 체크리스트

- [ ] sample_submission 인터페이스에 맞는 실행 코드와 설정
- [ ] 외부 API 호출 없음, 네트워크 없이 로컬 추론 가능
- [ ] 모델 가중치가 ZIP 안에 들어 있음 (실행 중 다운로드 없음)
- [ ] 출력 행 순서와 ID 형식이 sample_submission과 일치
- [ ] 질의 8,000개 모두 예측, 중복 ID 없음, 결측값 없음
- [ ] 질의마다 상위 5개가 의미 있는 순서로 채워짐
- [ ] 각 문항의 예측이 다른 문항에 의존하지 않음 (배치·순서를 바꿔도 결과 동일)
- [ ] ZIP 5GB 이하
- [ ] 깨끗한 환경에서 제출 패키지 실행 확인
- [ ] 이미지 16,000장 + 질의 8,000개를 900초 안에 여유 있게 처리

## <예시> 구현 참고안

> ⚠️ 아래는 **참고용 예시**다. 확정된 구현 계획이 아니며, 실제 데이터·환경·규정을 확인한 뒤 맞게 고쳐 쓴다.

### 예시 1. 평가와 데이터 분석

**평가 코드**
- 공식 지표와 같은 평가 코드를 만든다: 질의별 0.5 × (Hit@1 + NDCG@5)의 평균.
- 함께 기록할 지표: Hit@1, NDCG@5, Hit@5
- 초기 검색의 Hit@20/50/100을 따로 측정한다. 재정렬로 올릴 수 있는 상한을 보기 위해서다.

**로컬 검증 설계**
- Train 4,000쌍을 학습용과 검증용으로 나눈다.
- Test는 이미지가 텍스트의 2배다. 검증 gallery에도 정답이 아닌 이미지를 넣어 같은 비율에 가깝게 만든다. 예: 검증 텍스트의 정답 이미지 + 학습에 쓰지 않은 다른 이미지.
- 검증 gallery 크기가 Test(16,000장)보다 작으면 점수가 높게 나온다. 절대 점수보다 실험 간 비교에 쓴다.
- 같은 이미지·장면 그룹이 학습과 검증에 섞이는지 확인한다.
- 검증용 정답 이미지가 gallery에 **들어 있는 것**(정상)과 그 정답 쌍을 **학습에 쓰는 것**(누수)을 구분한다.

**데이터 분석**
- AI 생성 이미지라서 일반 사진으로 학습한 모델과 분포가 다를 수 있다. zero-shot 성능을 먼저 확인한다.
- 이미지 중복, 유사 이미지, 같은 객체·장면 그룹을 찾는다.
- query를 유형별로 나눠 오답을 분석한다.

  | 유형 | 예시 |
  |---|---|
  | 색상 | "빨간 자동차" |
  | 개수 | "개 두 마리" |
  | 행동 | "달리는 사람" |
  | 공간 관계 | "탁자 왼쪽의 고양이" |
  | 작은 객체 | 배경의 작은 사물 |
  | 이미지 속 문자 | 간판, 표지판 텍스트 |
  | 부정 표현 | "모자를 쓰지 않은 사람" |

### 예시 2. 빠른 baseline

**모델**
- 규정과 환경에 맞는 CLIP / SigLIP 계열 모델을 검토한다.
- 출처, 라이선스, 용량(ZIP 5GB 이내), 전처리를 확인한다.
- 이미지 인코더와 텍스트 인코더는 같은 체크포인트의 것을 쓴다.
- 텍스트 언어(한국어/영어)에 맞는 텍스트 인코더인지 확인한다.

**구현**
- 이미지 특징은 평가 중 한 번만 계산하고 모든 query에 재사용한다.
- 모델에 맞는 정규화와 유사도 계산을 적용한다.
- 검색은 먼저 PyTorch 행렬곱(정확 검색)으로 구현한다. 16,000 × 8,000 규모는 GPU 행렬곱으로 충분할 가능성이 크다. (추정, 측정 필요)
- image ID 매핑을 명시적으로 저장한다. 파일 순서에 의존하지 않는다.
- GPU를 여러 장 쓸 수 있으면 이미지 인코딩을 GPU별로 나눠 처리하는 것을 검토한다.

**시간 측정 구간**

| 구간 | 측정 |
|---|---|
| 초기화·모델 로딩 | ☐ |
| 이미지 읽기·디코딩·전처리 | ☐ |
| 이미지 인코딩 (16,000장) | ☐ |
| 텍스트 인코딩 (8,000개) | ☐ |
| 벡터 검색 | ☐ |
| 재정렬 | ☐ |
| 결과 생성 | ☐ |

- GPU는 비동기로 실행되므로 시간을 잴 때 동기화(`torch.cuda.synchronize()`)한다.
- 계측 범위가 확인되기 전까지는 로딩을 뺀 모든 구간이 900초에 포함된다고 보고 계획한다.

### 예시 3. 비슷한 후보의 디테일 구분

baseline은 그대로 두고 아래 개선을 하나씩 비교한다. 지표 특성상 **1위 정확도**를 올리는 개선을 우선한다.

**A. Top-K 재정렬**
- K 후보: 5 / 10 / 20 / 50
- 이미지–텍스트 매칭 모델이나 검증 가능한 소형 로컬 모델을 검토한다.
- 비싼 cross-modal 모델은 전체 이미지가 아니라 후보에만 적용한다.
- 긴 설명을 생성하는 방식보다 직접적인 매칭 점수를 먼저 검토한다.
- 초기 검색 점수와 재정렬 점수의 결합 방식은 검증셋에서 정한다.
- 재정렬 비용: 8,000 × K × 쌍당 비용. 남는 시간 예산 안에서 K를 정한다.

**B. 세부 속성**
- 색상, 객체 개수, 행동, 위치·관계 오류를 분석한다.
- 기본 입력은 원문 query다.
- 문장을 구조화·재표현할 때 객체와 속성의 연결, 부정, 수량, 왼쪽/오른쪽 관계를 보존한다.
- 속성 점수는 현재 query와 해당 후보 이미지만으로 계산한다.
- 검출 결과가 불확실하면 hard filtering을 과하게 쓰지 않는다.

**C. 학습 (Train 4,000쌍)**
- zero-shot baseline과 contrastive fine-tuning을 비교한다.
- 4,000쌍은 작으므로 과적합에 주의한다. 비용이 낮은 방식부터 비교한다: 작은 투영층 → 일부 층 학습 → LoRA 등.
- hard negative는 학습 split 안에서만 만든다.
- 이미지 전용 검색 head의 출력을 기존 텍스트 벡터와 바로 비교하지 않는다.
- 검증 split 라벨은 학습과 negative mining에 쓰지 않는다.

**D. 해상도와 crop**
- 원본 전체 이미지의 문맥을 유지한다.
- 작은 객체 때문에 실패하는 경우 고해상도나 추가 crop을 비교한다.
- 관계가 중요한 문장에서 crop이 문맥을 지우지 않는지 확인한다.
- 좌우 반전·색상 변경 증강이 query 의미를 깨뜨리지 않는지 확인한다.

### 예시 4. 시간과 용량 최적화

- baseline을 프로파일링하고 실제 병목부터 해결한다.

- 지원되면 FP16/BF16과 `torch.inference_mode()`를 쓴다.
- ANN은 벡터 검색 자체가 병목일 때만 비교한다. 정확 검색 대비 최종 점수를 함께 본다.
- 작은 표본의 속도를 단순 외삽한 값을 보장된 실행시간으로 쓰지 않는다. 가능하면 16,000장 규모로 측정한다.
- 900초에 여유가 있는 구성을 고른다.
- ZIP 실제 크기, 압축 해제 후 디스크, RAM, VRAM(장당 24GB) 사용량을 확인한다.

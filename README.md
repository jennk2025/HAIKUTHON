# HAIKUTHON — 텍스트→이미지 검색

자연어 설명에 가장 잘 맞는 이미지를 gallery에서 찾는 데이터톤이다.

> 이 문서의 본문에는 **대회 조건, 확인할 사항, 규정**만 정리했다.
> 구현 방법은 문서 끝의 **[<예시> 구현 참고안](#예시-구현-참고안)**에 따로 모았다. 정해진 계획이 아니고 참고용이다.

---

## 1. 대회 개요

| 항목 | 내용 |
|---|---|
| 과제 | 자연어 설명(query)에 가장 적합한 이미지를 검색한다 |
| 핵심 난점 | 비슷한 이미지 사이에서 색상, 객체, 개수, 행동, 위치, 객체 간 관계 등 문장의 디테일을 구분해야 한다 |
| 규모 | 이미지 수천~수만 장 (정확하고 빠른 검색 필요) |
| 평가 지표 | **NDCG@5** |
| 제출 방식 | 모델 압축 ZIP 업로드 → 평가 후 받은 CSV를 Kaggle에 제출 |
| 추론 제한 | 제출당 **900초**. 모델 로딩 등은 제외된다고 전달받았으나, 정확한 계측 범위는 공식 코드·문서로 확인 필요 |
| 제출 횟수 | 팀당 **25회** |
| ZIP 용량 | **5GB 이하** |
| 인터페이스 | sample_submission과 starter의 인터페이스를 따른다 |
| 금지 | 다른 문항의 예측 결과로 현재 문항의 예측을 보정·수정하는 행위 |
| 외부 API | 세부 허용 범위는 공식 규정으로 확인. 초기 구현은 로컬 모델과 로컬 검색만으로 완결한다 |

### 작업 원칙
- 아이디어만 나열하지 않는다. 가능한 작업은 코드와 측정 결과로 남긴다.
- 데이터·환경·규정에서 확인하지 못한 내용은 사실처럼 가정하지 않는다.
- 임의의 제출 인터페이스를 만들지 않는다.

| 제출 | ZIP 구조와 용량 제한의 정확한 기준 | ☐ |

## 3. 문항 독립성 규정

`predict(query, gallery, fixed_model)`의 결과는 다른 query의 내용, 처리 순서, 예측 결과에 의존하면 안 된다.

### 금지
- 다른 문항의 예측으로 현재 문항 점수를 보정
- test query 전체의 점수 통계로 정규화
- 전체 query 사이에서 정답 이미지를 일대일로 배정
- 이전 문항에서 고른 이미지를 현재 문항 후보에서 제거
- 다른 문항의 예측으로 의사 라벨을 만들어 적응

### 공식 규정으로 허용 여부를 확인할 사항
- gallery만으로 만든 임베딩 캐시·검색 인덱스
- gallery 사전 계산 결과를 제출 파일에 포함
- 현재 query 내부 후보들의 재정렬

독립적인 문항을 배치로 계산하는 것은 예측을 서로 보정하는 것과 다르다.

## <예시> 구현 참고안

> ⚠️ 아래는 **참고용 예시**다. 확정된 구현 계획이 아니며, 실제 데이터·환경·규정을 확인한 뒤 맞게 고쳐 쓴다.

### 예시 1. 평가와 데이터 분석

**평가 코드**
- 공식 지표와 일치하는 평가 코드를 만든다.
- 기록할 지표: NDCG@5, Top-1 accuracy, Hit@5
- 정답이 여러 개면 Recall@K와 Hit@K를 구분한다.
- 초기 검색의 Recall 또는 Hit@20/50/100을 따로 측정한다. 재정렬로 올릴 수 있는 상한을 보기 위해서다.

**데이터 분석**
- 이미지 중복, 유사 이미지, 같은 객체·장면 그룹을 찾는다.
- query를 유형별로 나눠 오답을 분석한다.

  | 유형 | 예시 |
  |---|---|
  | 색상 | "빨간 자동차" |
  | 개수 | "개 두 마리" |
  | 행동 | "달리는 사람" |
  | 공간 관계 | "탁자 왼쪽의 고양이" |
  | 작은 객체 | 배경의 작은 사물 |
  | 이미지 속 문자 | 간판, 표지판 텍스트 |
  | 부정 표현 | "모자를 쓰지 않은 사람" |

**누수와 검증 설계**
- 같은 이미지·원본·장면 그룹이 학습과 검증에 섞이는지 확인한다.
- 가능하면 실제 규모의 gallery와 distractor를 넣고 검증한다.
- 검증용 정답 이미지가 gallery에 **들어 있는 것**(정상)과 그 정답 쌍을 **학습에 쓰는 것**(누수)을 구분한다.

### 예시 2. 빠른 baseline

**모델**
- 규정과 환경에 맞는 CLIP / SigLIP 계열 모델을 검토한다.
- 출처, 라이선스, 다운로드 가능 여부, 용량, 전처리를 확인한다.
- 이미지 인코더와 텍스트 인코더는 같은 체크포인트의 것을 쓴다.

**구현**
- 이미지 특징은 문항마다 다시 계산하지 않는다.
- 캐시 키는 허용 범위 안에서 이미지와 모델·전처리 설정만으로 정한다.
- 모델에 맞는 정규화와 유사도 계산을 적용한다.
- 검색은 먼저 PyTorch 행렬곱 또는 Faiss Flat(정확 검색)으로 구현한다.
- image ID 매핑을 명시적으로 저장한다. 파일 순서에 의존하지 않는다.
- 점수 행렬이 크면 query나 gallery를 나눠 계산한다.

**시간 측정 구간**

| 구간 | 측정 |
|---|---|
| 초기화·모델 로딩 | ☐ |
| 이미지 읽기·디코딩·전처리 | ☐ |
| 이미지 인코딩 | ☐ |
| 인덱스 구축 | ☐ |
| 텍스트 인코딩 | ☐ |
| 벡터 검색 | ☐ |
| 재정렬 | ☐ |
| 결과 생성 | ☐ |

- GPU는 비동기로 실행되므로 시간을 잴 때 동기화(`torch.cuda.synchronize()`)한다.
- 캐시 없는 실행과 캐시 있는 실행의 시간을 따로 보고한다.

### 예시 3. 비슷한 후보의 디테일 구분

baseline은 그대로 두고 아래 개선을 하나씩 비교한다.

**A. Top-K 재정렬**
- K 후보: 20 / 50 / 100 등
- 이미지–텍스트 매칭 모델이나 검증 가능한 소형 로컬 모델을 검토한다.
- 비싼 cross-modal 모델은 전체 이미지가 아니라 후보에만 적용한다.
- 긴 설명을 생성하는 방식보다 직접적인 매칭 점수를 먼저 검토한다.
- 초기 검색 점수와 재정렬 점수의 결합 방식은 검증셋에서 정한다.
- 체크포인트마다 점수 스케일이 다른지 확인한다.

**B. 세부 속성**
- 색상, 객체 개수, 행동, 위치·관계 오류를 분석한다.
- 기본 입력은 원문 query다.
- 문장을 구조화·재표현할 때 객체와 속성의 연결, 부정, 수량, 왼쪽/오른쪽 관계를 보존한다.
- 속성 점수는 현재 query와 해당 후보 이미지만으로 계산한다.
- 검출 결과가 불확실하면 hard filtering을 과하게 쓰지 않는다.

**C. 학습**
- 학습용 정답 쌍이 충분하고 미세조정이 허용될 때만 진행한다.
- zero-shot baseline과 contrastive fine-tuning을 비교한다.
- hard negative는 학습 split 안에서만 만든다.
- 한 이미지에 설명이나 정답이 여럿이면 다른 정답을 negative로 쓰지 않는다.
- 비용이 낮은 방식부터 비교한다: 작은 투영층 → 일부 층 학습.
- 이미지 전용 검색 head의 출력을 기존 텍스트 벡터와 바로 비교하지 않는다.
- validation/test 라벨은 학습과 negative mining에 쓰지 않는다.

**D. 해상도와 crop**
- 원본 전체 이미지의 문맥을 유지한다.
- 작은 객체 때문에 실패하는 경우 고해상도나 추가 crop을 비교한다.
- 관계가 중요한 문장에서 crop이 문맥을 지우지 않는지 확인한다.
- 좌우 반전·색상 변경 증강이 query 의미를 깨뜨리지 않는지 확인한다.

### 예시 4. 시간과 용량 최적화

- baseline을 프로파일링하고 실제 병목부터 해결한다.
- 조정 대상: batch size, DataLoader worker 수, 이미지 디코딩
- 지원되면 FP16/BF16과 `torch.inference_mode()`를 쓴다.
- ANN은 벡터 검색 자체가 병목일 때만 비교한다. 정확 검색 대비 이웃 보존율과 최종 NDCG@5를 함께 본다.
- 임베딩 차원 축소·양자화는 필요할 때만 검토하고 점수 하락을 측정한다.
- 재정렬 비용 예산: query 수 × K × 쌍당 비용
- 작은 표본의 속도를 단순 외삽한 값을 보장된 실행시간으로 쓰지 않는다. 가능하면 전체 또는 대표 규모로 측정한다.
- 900초에 여유가 있는 구성을 고른다.
- ZIP 실제 크기, 압축 해제 후 디스크, RAM, VRAM 사용량을 확인한다.

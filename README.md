# HAIKUTHON — Multimodal RAG: 텍스트→이미지 검색

영문 텍스트 설명에 가장 잘 맞는 이미지를 비슷한 이미지들 사이에서 찾는 데이터톤이다.

> 이 문서의 본문에는 **대회 조건, 평가 방식, 규정, 확인할 사항**만 정리했다.
> - **[공식]**: 운영진 공지·설명 자료·공식 데이터셋/스타터 키트에 있는 내용
> - **[팀 조건]**: 팀이 스스로 정한 추가 작업 조건 (공식 규정과 구분)
> - **확인 필요**: 아직 공식으로 확인하지 못한 내용
>
> 구현 방법은 문서 끝의 **[<예시> 구현 참고안](#예시-구현-참고안)**에 따로 모았다. 정해진 계획이 아니고 참고용이다.

## 1. 대회 개요

| 항목 | 내용 |
|---|---|
| 주제 | Multimodal RAG — 영문 텍스트 설명에 가장 적합한 이미지 검색 |
| 출력 | query마다 전체 후보 이미지에서 **상위 5장을 순서대로** 반환 |
| 정답 | query마다 정답 이미지 **정확히 1장** |
| 핵심 난점 | 비슷한 이미지 사이에서 객체, 색상, 개수, 상태, 위치 관계 등 세부 속성을 구분 |
| 요구 사항 | 제한 시간 안에 모든 query 처리. 정확도와 연산 효율을 함께 고려 |
| 일정 | 2026-11-21 ~ 11-22 (무박 2일) |
| 링크 | [Train 데이터](https://huggingface.co/datasets/KimWooJin/26-haikuthon-train) · [모델 제출 사이트](https://2026-haikuthon.pages.dev/) · [Kaggle](https://www.kaggle.com/competitions/2026-haikuthon) |

### 데이터셋 [공식]

| 구분 | 규모 | 공개 여부 |
|---|---|---|
| Train | 이미지–영문 프롬프트 **4,000쌍** | Hugging Face 공개 |
| Test | 텍스트 **8,000개**, 후보 이미지 **16,000장** (설명 자료 기준) | **비공개**. 제출한 모델로 예측 CSV 생성 |

- 운영진이 직접 만든 **AI 생성 데이터**다. 각 이미지는 짝이 되는 프롬프트로 생성했다.
- Test 이미지가 비공개이므로 **이미지 임베딩을 미리 계산해 ZIP에 넣을 수 없다.**
- Test 후보 이미지가 텍스트의 2배다. 오답 이미지 구성 방식(비슷한 이미지끼리 짝을 지었는지 등)은 공지되지 않았다.

### Train 데이터 확인 결과 (2026-11-21, 로컬 다운로드본)

| 항목 | 결과 |
|---|---|
| 파일 | `images/<id>.png` 4,000장, `prompts.jsonl` 4,000줄 (`{"id": "0000", "prompts": "..."}`) |
| ID | `0000`~`3999` 연속, 이미지와 프롬프트 1:1 대응, 누락·중복 없음 |
| 이미지 | 전부 768×768 PNG, 총 3.65GB, PNG 헤더 이상 없음 (전체 디코딩 검사는 아직 안 함) |
| 프롬프트 | 17~72단어, 평균 36.4단어 |
| 문장 구조 | 정해진 틀로 생성됨. 개수("One ..."), 색상·무늬, 위치 관계(above / left of / next to), 장소, 화풍, 시점, 조명을 포함 |

### 작업 원칙
- 아이디어만 나열하지 않는다. 가능한 작업은 코드와 측정 결과로 남긴다.
- 데이터·환경·규정에서 확인하지 못한 내용은 사실처럼 가정하지 않는다.
- 임의의 제출 인터페이스를 만들지 않는다. 스타터 키트의 `model.py` 인터페이스를 따른다.

## 2. 평가 방식 [공식]

### 최종 점수

| 구성 | 비중 | 세부 |
|---|---|---|
| 리더보드 점수 | **70%** | Public **40%** + Private **60%**. Private 점수는 제출 마감 이후 공개 |
| 발표 점수 | **30%** | 상위 10팀 결선 진출. 발표 6분 + 질의응답 2분. 심사위원 4명 |

- 발표 평가 항목: 전달력, 방법론의 타당성, 독창성, 실험 근거, 심사위원 자유 점수
- 리더보드는 Private 비중이 더 크다. Public 점수에만 맞춘 조정은 피하고, 로컬 검증에서 개선된 구성만 제출한다.
- 발표에서 모델 선택 이유, 요소별 효과, 실패한 시도를 설명할 수 있도록 [`PUSH_LOG.md`](PUSH_LOG.md)에 계속 기록한다.

### 검색 점수

```
질의별 점수   = 0.5 × (Recall@1 + NDCG@5)
최종 검색 점수 = 전체 질의별 점수의 평균
```

- `r` = 정답 이미지의 검색 순위
- **Recall@1** (= Hit-Ratio@1): r = 1이면 1, 아니면 0
- **NDCG@5**: r ≤ 5이면 1 / log2(r + 1), 아니면 0

| 정답 순위 r | Recall@1 | NDCG@5 | 질의 점수 |
|---|---|---|---|
| 1 | 1 | 1.000 | **1.000** |
| 2 | 0 | 0.631 | 0.315 |
| 3 | 0 | 0.500 | 0.250 |
| 4 | 0 | 0.431 | 0.215 |
| 5 | 0 | 0.387 | 0.193 |
| 6 이상 | 0 | 0 | 0 |

- 1위와 2위의 차이(0.685)가 2위와 탈락의 차이(0.315)보다 훨씬 크다. **정답을 1위에 놓는 정확도가 가장 중요하다.**
- 2~5위도 부분 점수가 있으므로 상위 5개를 모두 의미 있는 순서로 채운다.

## 3. 실행 환경과 제출 규칙 [공식]

### 채점 서버

| 항목 | 내용 |
|---|---|
| GPU | 제출 1건당 NVIDIA **L4 (24GB) 1장**. GPU 여러 장이 한 제출을 병렬로 처리하지 않는다 |
| 서버 구성 | L4 1장씩 할당된 독립 서버 2~10대. 제출 트래픽에 따라 대수가 바뀌고, 몰리는 시간에는 채점 대기가 생긴다 |
| 추론 시간 | 제출 1회당 최대 **15분(900초)**, GPU 1장 기준. 모델 로딩 시간 등을 제외한 추론 시간만 측정 |
| 제출 횟수 | 팀당 최대 **25회** |
| ZIP 용량 | **5GB 이하** |

### 제출 절차
1. 모델 ZIP을 [모델 제출 사이트](https://2026-haikuthon.pages.dev/)에 올린다.
2. 평가가 끝나면 예측 CSV를 내려받는다.
3. 그 CSV를 Kaggle에 제출한다.

마감 직전에는 채점 대기가 길어질 수 있다. 최종 후보는 여유 있게 미리 제출한다.

### 제출 인터페이스 (스타터 키트 `sample_submission/model.py`)

```
submission.zip
├── model.py            # ZIP 최상위에 둔다
├── requirements.txt
└── models/             # 가중치·설정. 경로는 model.py에서 정한다
```

```python
load_model(model_dir, device) -> model      # model_dir: ZIP을 푼 최상위 경로. 반환 형태는 자유
predict(model, queries, candidates, top_k=5) -> dict
```

| 인자 / 반환값 | 형식 |
|---|---|
| `queries` | `[{"prompt_id": ..., "prompt": "영문 문장"}, ...]` |
| `candidates` | `[{"image_id": ..., "image_path": 파일 경로}, ...]` |
| 반환값 | `{prompt_id: [image_id 5개, 1위부터 순서대로]}` |

- 서버는 `predict()`를 한 번 호출하면서 query 전체와 후보 이미지 전체를 넘긴다.
- 이미지 읽기와 인코딩이 `predict()` 안에서 일어난다. 따라서 **이미지 16,000장 인코딩이 900초 안에 들어간다고 보고 계획한다.** (계측 범위는 확인 필요)
- 예제 `requirements.txt`에 따르면 서버에는 `transformers==5.22.2`, `safetensors==0.8.0`, `sentencepiece==0.2.3`, `pillow==13.0.0`이 기본 설치되어 있다.

### 공식 baseline (스타터 키트)

| 항목 | 내용 |
|---|---|
| 모델 | `google/siglip-base-patch16-224` (약 203M 파라미터, 가중치 0.81GB) |
| 입력 | 이미지 224px로 축소, 텍스트 최대 64토큰 (넘으면 잘림) |
| 학습 | 이미지·텍스트 출력 헤드만 학습, 1에포크, 배치 16, lr 1e-5, SigLIP 손실 |
| 검증 | 시드 42로 3,200 / 800 분할. 검증 이미지 800장 전체를 후보로 Top-5 검색 |
| 공식 검증 점수 | Recall@1 **0.6925**, NDCG@5 **0.8752**, 평균 **0.7839** (운영진이 Apple Silicon에서 측정) |

- 64토큰을 넘어 뒷부분이 잘리는 프롬프트는 **38개(0.9%)**, 토큰 수 중앙값 42, 최대 77이다(외부 저장소 [haikuthon-mmrag](https://github.com/jaeuk6797-cell/haikuthon-mmrag) `experiments.md`의 측정값). 처음에 "수백 개"로 추정했던 것은 틀렸다. SigLIP 토크나이저는 문장부호를 지우고 소문자로 바꾸는데, 단어와 문장부호를 함께 세서 과하게 추정했다.
- 검증 후보가 800장(텍스트와 1:1)이라서, 후보 16,000장(텍스트의 2배)인 test보다 점수가 높게 나올 가능성이 크다(추정).

## 4. 규정

### 4-1. 공식 금지 사항
1. **외부 API 호출 금지.** 추론은 ZIP에 넣은 로컬 모델과 코드만으로 끝나야 한다.
2. **다른 문항의 예측 결과로 현재 문항의 예측을 보정·수정하는 행위 금지.**
3. **외부 closed-weight 생성형 AI로 학습 데이터 증강 금지.** 예: GPT-Image, Nano-Banana
4. **GPT, Claude 등 LLM으로 학습 데이터 증강 금지.**
5. **학습에는 Google Colab과 Kaggle의 무료 GPU만 사용.**

**허용 [공식]**: 로컬 VLM, 로컬 생성형 모델은 사용할 수 있다.

위반하면 해당 팀의 결과가 순위 산정에서 제외될 수 있다. 문의는 운영진을 통해서 한다.

**해석과 주의**
- "로컬"은 외부 API나 호스팅 서비스가 아니라 **우리가 직접 가중치를 받아 실행하는 모델**로 본다. 5번 규정이 있으므로 직접 실행하는 장소도 무료 Colab / Kaggle로 한다.
- 4번은 GPT, Claude 같은 서비스형 LLM을 겨냥한 것으로 보인다. 오픈 가중치 LLM을 로컬에서 돌려 증강하는 것은 "로컬 생성형 모델"로 허용되는 것으로 해석했다. (확인 권장)
- **Claude Code는 코드 작성에만 쓴다.** Claude가 증강용 문장이나 negative 캡션을 직접 써서 학습 데이터에 넣지 않는다. 증강 데이터는 규칙 기반 스크립트나 로컬 모델이 만든다.

### 4-2. 팀 조건 (공식 규정보다 엄격하게 정한 것)
- 증강 단계에서도 Claude·GPT 등 상용 생성 서비스나 API를 쓰지 않는다.
- 모델 기반 증강에는 오픈소스 모델을 실행 환경 안에서 직접 구동한다. 오픈소스 모델이라도 외부 호스팅 추론 API는 쓰지 않는다.
- 공개 가중치라는 이유만으로 오픈소스로 보지 않는다. 라이선스와 대회 사용 가능 여부를 확인하고 기록한다.
- 학습뿐 아니라 **증강 생성과 검증도 무료 Colab / Kaggle에서 실행**한다. 5번 규정의 "학습"에 증강 생성이 포함되는지 불분명하므로 안전한 쪽으로 정했다.
- 유료 GPU, 유료 구독, 유료 API, 다중 GPU를 전제로 설계하지 않는다. 무료 환경에서 실제로 할당된 GPU 메모리와 세션 제한에 맞춰 모델과 배치 크기를 정한다.

### 4-3. 문항 독립성 (공식 금지 사항 2번)

`predict(query, gallery, fixed_model)`의 결과는 다른 query의 내용, 처리 순서, 예측 결과에 의존하면 안 된다.

**해당하는 것으로 보는 예**
- 다른 문항의 예측으로 현재 문항 점수를 보정
- test query 전체의 점수 통계로 정규화
- 전체 query 사이에서 정답 이미지를 일대일로 배정 (예: query 8,000개와 이미지 16,000장을 헝가리안 매칭)
- 이전 문항에서 고른 이미지를 현재 문항 후보에서 제거
- 다른 문항의 예측으로 의사 라벨을 만들어 적응

**해당하지 않는 것으로 보는 예** (공식 확인 권장)
- 독립적인 문항을 배치로 묶어 계산. 결과가 배치 구성과 무관하면 보정이 아니다
- 후보 이미지만으로 만든 임베딩을 평가 중에 한 번 계산해 모든 query에 재사용. 스타터 키트도 이렇게 한다
- 현재 query 하나의 후보들 안에서 재정렬

## 5. 확인할 사항

확인된 항목은 ✅, 아직 확인하지 못한 항목은 ☐로 표시한다.

| 분류 | 확인 항목 | 상태 | 메모 |
|---|---|---|---|
| 지표 | 평가 지표 정의 | ✅ | 0.5 × (Recall@1 + NDCG@5) |

**요약 (2026-11-21 측정)**
- 오류 0건. ID `0000`~`3999`가 이미지 4,000장과 1:1로 맞고, 누락·손상·중복 ID·빈 설명이 없다. 이미지는 모두 768×768 RGB PNG다.

### 예시 1. 평가와 데이터 분석

**평가 코드**
- 공식 지표와 같은 평가 코드를 만든다: 질의별 0.5 × (Recall@1 + NDCG@5)의 평균.
- 함께 기록할 지표: Recall@1, NDCG@5, Hit@5
- 초기 검색의 Hit@20/50/100을 따로 측정한다. 재정렬로 올릴 수 있는 상한을 보기 위해서다.

**로컬 검증 설계**
- 공식 분할(시드 42, 3,200 / 800)을 기준선으로 그대로 재현해 공식 점수 0.7839와 비교한다.
- Test는 후보 이미지가 텍스트의 2배다. 검증 후보에도 정답이 아닌 이미지를 넣어 비율을 맞춘 설정을 따로 만든다.
- 검증 후보 수와 구성을 실험마다 기록한다. 후보가 적으면 점수가 높게 나오므로 절대 점수보다 실험 간 비교에 쓴다.
- 증강 데이터는 학습 분할에서만 만든다. 원본과 증강본이 학습·검증에 나뉘어 들어가지 않게 한다.
- 검증용 정답 이미지가 후보에 **들어 있는 것**(정상)과 그 정답 쌍을 **학습에 쓰는 것**(누수)을 구분한다.

**데이터 분석**
- AI 생성 이미지라서 일반 사진으로 학습한 모델과 분포가 다를 수 있다. zero-shot 성능을 먼저 확인한다.
- 프롬프트가 정해진 틀로 생성됐으므로 속성(개수, 색상, 무늬, 관계, 장소, 화풍, 시점, 조명)을 규칙으로 뽑아 오답 유형을 분석할 수 있다.

  | 유형 | 예시 |
  |---|---|
  | 색상·무늬 | "polka-dotted and orange" |
  | 개수 | "One ...", 객체 수 |
  | 상태·행동 | "lying", "open", "closed" |
  | 공간 관계 | "above", "to the left of", "next to" |
  | 장소 | "in a kitchen", "on a patio" |
  | 화풍·시점·조명 | "watercolor", "side view", "warm indoor lighting" |

### 예시 2. baseline 재현과 빠른 개선

**baseline**
- 스타터 키트 `train.py`를 무료 Colab / Kaggle에서 그대로 실행해 공식 점수와 비교한다.
- 시간 측정: L4와 비슷한 무료 GPU(T4 등)에서 이미지 16,000장 인코딩 시간을 재고 L4 기준으로 여유를 둔다. T4와 L4의 속도 차이는 추정으로 표시한다.

**먼저 볼 개선 후보**
- 텍스트 길이 제한: 64토큰에서 잘리는 프롬프트 수를 토크나이저로 세고, 잘린 부분에 어떤 정보가 있는지 본다.
- 해상도: 224px보다 높은 해상도의 체크포인트를 비교한다.
- 더 큰 모델: SigLIP / SigLIP2 계열의 더 큰 체크포인트. 라이선스, 용량(5GB 이내), 900초 안의 인코딩 시간을 함께 본다.
- 학습 범위: 출력 헤드만 → 일부 층 / LoRA. 4,000쌍은 작으므로 과적합에 주의한다.

**구현**
- 이미지 특징은 `predict()` 안에서 한 번만 계산하고 모든 query에 재사용한다.
- 검색은 먼저 PyTorch 행렬곱(정확 검색)으로 구현한다.
- image ID 매핑을 명시적으로 저장한다. 파일 순서에 의존하지 않는다.
- 이미지 디코딩이 병목이면 DataLoader worker로 병렬 처리한다.

**시간 측정 구간**

| 구간 | 측정 |
|---|---|
| 모델 로딩 (`load_model`, 계측 제외로 공지) | ☐ |
| 이미지 읽기·디코딩·전처리 (16,000장) | ☐ |
| 이미지 인코딩 | ☐ |
| 텍스트 인코딩 (8,000개) | ☐ |
| 벡터 검색 | ☐ |
| 재정렬 | ☐ |

- GPU는 비동기로 실행되므로 시간을 잴 때 동기화(`torch.cuda.synchronize()`)한다.

### 예시 3. 비슷한 후보의 디테일 구분

baseline은 그대로 두고 아래 개선을 하나씩 비교한다. 지표 특성상 **1위 정확도**를 올리는 개선을 우선한다.

**A. Top-K 재정렬**
- K 후보: 5 / 10 / 20 / 50
- 이미지–텍스트 매칭 모델이나 검증 가능한 소형 로컬 모델을 검토한다.
- 비싼 cross-modal 모델은 전체 이미지가 아니라 후보에만 적용한다.
- 초기 검색 점수와 재정렬 점수의 결합 방식은 검증셋에서 정한다.
- 재정렬 비용: 8,000 × K × 쌍당 비용. 이미지 인코딩 후 남는 시간 안에서 K를 정한다.

**B. 세부 속성**
- 색상, 개수, 상태, 위치·관계 오류를 분석한다.
- 문장을 구조화·재표현할 때 객체와 속성의 연결, 수량, 왼쪽/오른쪽 관계를 보존한다.
- 속성 점수는 현재 query와 해당 후보 이미지만으로 계산한다.
- 검출 결과가 불확실하면 hard filtering을 과하게 쓰지 않는다.

**C. 학습과 증강**
- hard negative는 학습 분할 안에서만 만든다. 예: 프롬프트의 속성 하나(색상, 관계 등)만 바꾼 텍스트를 negative로 쓴다.
- 이미지를 바꾸는 증강(좌우 반전, 색 변경)은 텍스트의 "left / right", 색상과 어긋나지 않는지 확인한다. 어긋나면 텍스트도 함께 고치거나 쓰지 않는다.
- 생성 모델 증강은 라이선스를 확인한 로컬 모델(VLM, 이미지 생성 모델 등)만, 무료 Colab / Kaggle에서 직접 실행한다.
- 로컬 VLM 활용 예: 생성한 증강 이미지가 바뀐 텍스트와 실제로 맞는지 검사, 학습 이미지의 속성 확인.
- 프롬프트가 정해진 틀이라서 텍스트 증강(속성 바꾸기, 문장 순서 바꾸기)은 LLM 없이 규칙 기반 스크립트로 할 수 있다.

### 예시 4. 시간과 용량 최적화

- baseline을 프로파일링하고 실제 병목부터 해결한다.
- 조정 대상: batch size, DataLoader worker 수, 이미지 디코딩
- 지원되면 FP16/BF16과 `torch.inference_mode()`를 쓴다.
- 작은 표본의 속도를 단순 외삽한 값을 보장된 실행시간으로 쓰지 않는다. 가능하면 16,000장 규모로 측정한다.
- 900초에 여유가 있는 구성을 고른다.
- ZIP 실제 크기, 압축 해제 후 디스크, RAM, VRAM(24GB) 사용량을 확인한다.

### 예시 5. 문항 독립성 테스트

- 배치 구성과 query 순서를 바꿔도 각 문항의 순위가 수치 오차 범위 안에서 같은지 확인한다.

### 예시 6. 실험 관리

- 먼저 동작하는 baseline을 완성한다.
- 실험마다 설정, 분할, 검증 후보 수, seed, 체크포인트, 지표, 시간, VRAM, 모델 용량, 실행 환경, 실행 명령을 기록한다.
